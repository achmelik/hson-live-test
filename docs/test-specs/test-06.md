# Test 06: Chart library integration

## 1. Test ID and name

**Test ID:** 06  
**Test name:** Chart library integration

---

## 2. What is being tested

How hson-live coexists with a third-party DOM library that manages its own subtree (a chart library) without being ingested by hson-live's LiveTree.

Specifically:
- A page contains both hson-live-managed content (via LiveTree) and a chart library that owns and renders its own DOM region (typically a `<canvas>` or contained `<div>`).
- The chart library and LiveTree operate independently; the library's DOM is NOT parsed into the node graph.
- LiveTree mutations, style changes, and DOM updates must not disrupt the chart library's rendering or state.
- Multiple chart types (line, bar, pie, scatter, or equivalent variety) must be rendered on the same page to verify the pattern holds across different chart implementations.
- No real websocket, SSE, or other non-standard transport; any dynamic updates are mocked or triggered by standard DOM events (click, input).

---

## 3. How it will be tested

**Page structure:**
- A page with a container managed by hson-live (root element or subtree).
- Multiple chart regions within or alongside the hson-live container, each hosting a separate chart library instance.
- Chart data and configuration provided statically (fixture) or via mocked state (e.g., closure or module variable).

**Approach:**
- Initialize a LiveTree over a container element, establishing a managed region.
- Within that container, render multiple distinct chart types (minimum 2 types) using a popular, maintained chart library.
- Apply LiveTree mutations (node creation, removal, style changes, content replacement) to parts of the page that do NOT contain charts.
- Trigger chart re-renders or state updates via mocked listeners (e.g., on-click handlers that update chart data).
- Verify:
  - Charts render without visual artifacts or corruption.
  - Chart interactivity (hover, click, legend interaction) remains functional.
  - LiveTree DOM updates do not interfere with chart DOM or canvas rendering.
  - No console errors related to the chart library.
  - Memory (detectable via browser DevTools) does not leak across mutation cycles.

**Instrumentation:**
- Browser console (error/warning detection).
- Visual comparison (chart dimensions, rendering artifacts).
- DOM structure inspection (chart container and chart library markers intact).
- Event listener verification (chart click handlers still attached and functional).
- Performance observation: track frame rate or paint timing over a sequence of operations.

**Fixtures required:**
- Fixture providing sample chart data (e.g., datasets for line, bar, pie charts).
- Chart configuration objects (no literal JSON/data; describe required structure: labels, values, colors, axes, etc.).
- No HTML fixture; page structure is minimal and generated by the test.

---

## 4. Likely failure modes and how they will be detected

| Failure Mode | Detection Method |
|---|---|
| LiveTree DOM mutation overwrites or removes a chart container. | DOM traversal inspection; chart missing from final DOM; console error from library attempting to render missing element. |
| LiveTree style changes cascade into chart container (e.g., inherited CSS filters, transform, opacity). | Visual comparison (chart distorted, hidden, or color-shifted); computed style inspection. |
| Chart library event handlers detached during LiveTree mutation. | Chart click/hover listeners non-functional; no event log from mocked chart handlers. |
| Chart canvas/SVG context corrupted or redrawn incorrectly after LiveTree operation. | Visual inspection; mismatch between expected chart image and actual rendering. |
| Memory growth during repeated LiveTree mutations and chart re-renders. | Memory profiler showing monotonic growth; heap snapshots before/after cycles. |
| Z-index or stacking context issues between hson-live content and chart. | Visual inspection; chart occluded by overlapping LiveTree content or vice versa. |
| Chart library throws error when hson-live container is resized or reflowed. | Console error capture; chart rendering halts or throws unhandled exception. |

## 5. Measurement

**Primary metrics:**
- **Chart render success rate:** Percentage of chart types that render without error across all operations (target: 100%).
- **Interactivity preservation:** Chart interactions (click, hover) remain responsive after LiveTree mutations (binary: pass/fail).
- **DOM integrity:** Chart container and its children (canvas or nested elements) remain in the final DOM tree (binary: pass/fail).
- **Console cleanliness:** No errors or warnings logged by the chart library or hson-live during the test (count: 0 errors).
- **Frame rate stability:** Frame rate remains consistently stable during chart rendering and LiveTree updates (no sustained drops).
- **Memory stability:** Heap growth over 10 mutation cycles + re-render cycles remains within acceptable limits (differential measurement; no monotonic growth).

**Secondary metrics:**
- Time to first chart render (milliseconds).
- Time to update chart data and re-render (milliseconds).
- Peak memory usage during the test cycle (bytes).

## 6. Report shape

Report accessible from browser frontend (in-browser primary). No shared contract across tests.

**Report structure (browser-rendered):**
- **Test metadata:** Test ID, name, start/end timestamps, overall result (pass/fail).
- **Chart render results:** Table with columns: Chart Type | Rendered | Interactive | No Errors
- **DOM inspection results:** Presence of chart containers, element counts, final DOM structure snapshot.
- **Console log summary:** Count of errors, warnings, and info messages; excerpts of any errors.
- **Performance data:** Frame time histogram (median, p95, min, max); memory graph (baseline, peak, final).
- **Interactivity verification:** List of tested interactions (e.g., click chart legend, hover data point) and whether each fired its handler.
- **Visual comparison:** Before/after screenshots of each chart type (if possible), or descriptive text ("Chart rendered, no artifacts").
- **Test result summary:** Pass (all checks met) or Fail (list failed checks).

Storage: JSON file written to disk (location and naming scheme open to implementation); consumed by browser-side renderer to populate an HTML report.

## 7. Out of scope

- Testing hson-live's own transformation or serialization logic (core library behavior).
- Testing the chart library's internal algorithms, performance, or feature completeness.
- Testing websocket or real-time data feeds; any dynamic updates are mocked.
- Testing hson-live's behavior with untrusted HTML or HTML sanitization.
- Testing accessibility (ARIA, keyboard navigation) of the page or charts.
- Testing responsive design or mobile viewport behavior.
- Testing SSO, authentication, or server-side session state.
- Testing the chart library in isolation (outside an hson-live context).
- Testing visual rendering at high zoom levels or with custom fonts.
- Testing chart library plugins or advanced third-party extensions.

## 8. Tech stack required

**Frontend:**
- hson-live (main package, /root export).
- A popular, currently-maintained chart library (e.g., Chart.js, Recharts, Apache ECharts, Plotly.js, or D3.js wrapper). Library choice is up to the implementing agent; only requirement is popularity and active maintenance.
- Browser: modern Chrome/Firefox/Edge with support for modern DOM APIs and canvas/SVG rendering.
- Test instrumentation: browser DevTools capabilities for console inspection and performance measurement.

**Backend:**
- A simple HTTP server capable of serving HTML pages and static assets. Build tools and framework details are implementation choices.

**Mocking:**
- Chart data updates triggered by DOM events (click, input) with mocked event handlers.
- No real websockets or SSE; state updates via module-level variables or object mutations, not backend.

---

## 9. Mocking notes

**Chart library render:**
- Chart library is real, not mocked. It renders into its own DOM region (canvas or div).

**Data updates:**
- Chart data updates are triggered by user interaction (click, input change) on the page.
- Mocked via closure-captured state or a simple event emitter, not a backend socket or fetch.
- Example: clicking an "Update Data" button mutates a data object in memory, chart library's update method is called, chart re-renders.

**Dynamic content outside charts:**
- Any LiveTree mutations (node creation, deletion, style changes) outside the chart region are real (not mocked).
- Chart containers themselves are never mutated by LiveTree; they are static containers.

## 10. Assumptions and open questions

### Assumptions made

1. **Chart library isolation:** The chart library manages a discrete DOM region (e.g., `<div id="chart1">` or `<canvas>`), and hson-live will not attempt to graft or project into that region.
2. **No LiveTree-chart interaction:** hson-live does not manage, query, or modify chart DOM directly. Interactions are only side-by-side.
3. **Chart data is static or client-side mutable:** Chart data is provided as a fixture or stored in memory; no backend polling, websocket, or SSE.
4. **Mutation zone separation:** LiveTree mutations occur in a distinct region of the page (not inside chart containers). If mutations occur near or adjacent to charts (e.g., sibling elements), they do not remove or reconfigure chart containers themselves.
5. **Multiple chart types:** At least two distinct chart types (e.g., line and bar, or pie and scatter) must be exercised. Rendering the same type twice does not satisfy the variety requirement.
6. **Browser environment:** Test runs in a real browser (not JSDOM or Headless Chrome with canvas mocking), since chart libraries often rely on actual canvas/SVG rendering.
7. **No real-time feeds:** Chart updates are triggered by user interaction or mocked timers, not live data streams.

### Scope expansions

None identified. The spec adheres strictly to the parent scope: testing hson-live's coexistence with a third-party chart library.

### Open questions

1. **Chart library choice:** Which specific chart library should be used? Recommendation: Chart.js (widespread, simple setup) or Apache ECharts (richer chart types, active maintenance). Agent may choose; constraint is popularity and active maintenance only.
2. **Number of chart instances:** Is "multiple chart types" 2 types minimum, or higher? Interpretation: at least 2 distinct types (not 2 instances of the same type).
3. **LiveTree scope:** Should the entire page be managed by a single LiveTree, or should only a sidebar/section be LiveTree-managed? Interpretation: any arrangement that demonstrates independent operation is acceptable, as long as chart containers are outside or explicitly protected.
4. **Memory testing environment:** Should memory profiling use browser DevTools heap snapshots (manual), or automated memory observer API? Recommend browser DevTools for clarity; automation optional.
5. **Visual comparison baseline:** Should baseline chart images be captured and compared programmatically, or is visual inspection sufficient? Recommend programmatic comparison if feasible; visual spot-check acceptable if not.
6. **Mutation intensity:** How many LiveTree mutations should be performed before/after chart updates? Interpretation: enough to verify stability (e.g., 10 cycles of mutation + chart re-render).
